# Бриф проекта: сервис подсказок на базе нейросети для игры по финансовой грамотности

Документ для разработчика или ИИ-агента, который будет реализовывать сервис. Здесь описаны суть проекта, принятые решения, контракт API, структура кода, админская часть и открытые вопросы. Если что-то не описано явно, не придумывай правила игры: заложи расширяемое место и пометь его `TODO`.

---

## 1. Контекст

Команда разрабатывает мобильную игру на **Flutter** по финансовой грамотности. Механика похожа на игру *No Time to Relax*: пошаговая игра, где игрок управляет распорядком персонажа и набирает очки по нескольким показателям (деньги, здоровье, образование, счастье). Действия привязаны к локациям (банк, работа, университет и т.д.), стоят игрового времени и влияют на показатели. Бывают события, сроки (например, рента) и ограниченное число ходов.

**Задача этого сервиса:** по текущему состоянию игрока и списку доступных ходов подсказать, какой ход выгоднее, чтобы Flutter-приложение подсветило нужную кнопку.

**Зона ответственности:** только бэкенд-эндпоинт подсказок и его админская часть. Интерфейс игры и подсветка кнопок делаются на стороне Flutter другим человеком.

## 2. Ключевые решения (уже приняты)

| Решение | Суть |
|---|---|
| Стек | Java + **Spring Boot** (Maven) |
| Нейросеть | Внешний **LLM по API** (провайдер пока не выбран, слой изолирован за интерфейсом клиента) |
| Клиент → нейросеть | Напрямую **нельзя**: ключ API нельзя прятать в приложении, нужен контроль промпта, лимитов и ответа. Всегда через этот сервис |
| Как нейросеть «управляет» кнопкой | Не управляет. Возвращает только `id` хода, а Flutter сам сравнивает `action.id == recommendedActionId` и подсвечивает кнопку |
| Арифметику считает код, не модель | Для каждого хода сервис считает оценку по правилам игры (`ActionScorer`), модель получает готовые числа, выбирает и объясняет |
| Запасной вариант | При таймауте, ошибке API или некорректном ответе возвращается ход с лучшей оценкой по правилам (`source = "rules"`). Игра не должна ломаться из-за подсказки |
| Ответ модели строго по схеме | Tool use (function calling) с принудительным вызовом инструмента; допустимые `id` передаются как `enum`. Проверка `id` на стороне сервиса остаётся обязательной |
| Состояние игры | Пока предполагается, что **приходит в запросе** (см. открытые вопросы) |
| Кэш | На старте **не делаем** (добавить, когда по логам видно повторяющиеся запросы) |
| Лимит подсказок | Простой счётчик в памяти внутри `HintService`, без отдельного класса, пока не разрастётся |
| База данных | Нужна **только из-за админки** (версии промптов, настройки, журнал). Для самой подсказки не нужна |

## 3. Поток обработки запроса

```
Flutter → POST /api/v1/hint
  1. Контроллер: валидация формата (@Valid)
  2. HintService: проверка лимита подсказок
  3. ActionScorer: оценка каждого хода по правилам игры
  4. PromptBuilder: активная версия промпта + данные запроса
  5. LlmClient: вызов API нейросети (структурированный ответ)
  6. HintService: проверка, что вернувшийся id есть в списке ходов
  7. При любом сбое на шагах 5–6: ход с лучшей оценкой (source = "rules")
  8. Ответ: { recommendedActionId, reason, source }
```

## 4. Контракт API (игровой)

### `POST /api/v1/hint`

Запрос (состав полей уточняется по правилам игры, ниже пример для NTTR-подобной механики):

```json
{
  "gameId": "a1b2c3",
  "turn": 7,
  "totalTurns": 20,
  "stats": { "money": 1200, "health": 40, "education": 1, "happiness": 55 },
  "inventory": ["fridge"],
  "job": { "id": "market_6", "experience": 180 },
  "housing": { "type": "cheap", "rentDueInTurns": 1, "rentAmount": 200 },
  "currentEvent": { "id": "crime_wave" },
  "timeLeftThisTurn": 120,
  "availableActions": [
    { "id": "work", "location": "market", "timeCost": 40, "effect": "+50 money, +6 exp" },
    { "id": "study", "location": "university", "timeCost": 60, "effect": "+1 education progress" },
    { "id": "deposit", "location": "bank", "timeCost": 20, "effect": "money -> savings" }
  ]
}
```

Ответ:

```json
{
  "recommendedActionId": "deposit",
  "reason": "До аренды ещё есть запас, а вклад приносит процент за ход.",
  "source": "llm"
}
```

Правила контракта:
- `id` хода **стабильный** (не меняется при смене подписи или перевода). Подписи (`label`) могут меняться.
- Модель обязана выбрать `id` **только из** `availableActions`. Иначе сервис использует запасной вариант.
- `totalTurns` (или число оставшихся ходов) обязательно: оптимальная стратегия зависит от длины партии.
- Ошибка нейросети **не приводит к ошибке для клиента**: возвращается 200 с `source: "rules"`.
- Коды ошибок: 400 (некорректный запрос), 429 (лимит подсказок исчерпан), 500 (непредвиденное).
- Возможное расширение: двухуровневая подсказка (`recommendedLocationId` + `recommendedActionId`), если в игре сначала выбирают локацию, а потом действие. Решение зависит от дизайна игры.

## 5. Админская часть

Админ (разработчик или геймдизайнер) должен иметь возможность править промпт и настройки сервиса без пересборки и перезапуска.

### Что можно менять через админку
- системный промпт (роль, критерий «выгодно», стиль объяснения);
- модель, `max_tokens`, температуру, таймаут вызова;
- лимит подсказок на партию;
- переключатель «использовать нейросеть» (аварийный выключатель: при выключении сервис отвечает только по правилам);
- числовые параметры `ActionScorer` (веса, пороги).

### Что остаётся в коде
- схема структурированного ответа (`enum` допустимых `id`) и проверка `id` (сломанный промпт не должен приводить к несуществующей кнопке);
- запасной вариант по правилам;
- сами формулы `ActionScorer` (через админку меняются только их параметры, не код);
- **API-ключ нейросети**: только переменная окружения, через админку не меняется и не показывается.

### Админский API (префикс отдельный от игрового)

```
GET    /api/v1/admin/prompts                  список версий промпта
POST   /api/v1/admin/prompts                  создать новую версию
POST   /api/v1/admin/prompts/{id}/activate    сделать версию активной (так же делается откат)
GET    /api/v1/admin/settings                 текущие настройки
PUT    /api/v1/admin/settings/{key}           изменить настройку
POST   /api/v1/admin/test-hint                пробный прогон: черновик промпта + тестовое состояние → ответ модели, ничего не активируя
GET    /api/v1/admin/audit                    журнал изменений
```

Пробный прогон (`test-hint`) обязателен: правка промпта «вслепую» на живых игроках рискованна.

### Схема БД (минимум)

```
prompt_version: id, text, created_at, created_by, active (boolean), comment
setting:        key, value, updated_at, updated_by
audit_log:      id, who, what, old_value, new_value, at
```

Принципы:
- версии промптов **не перезаписываются**: правка создаёт новую версию, активна ровно одна; откат это переключение активной версии;
- каждое изменение настроек и промптов пишется в `audit_log`;
- PostgreSQL для окружений, H2 допустима локально; миграции через **Flyway**;
- настройки и активный промпт кэшируются в памяти сервиса и обновляются при записи (при нескольких экземплярах сервиса добавить периодическое обновление из БД).

### Безопасность админки
- роли `USER` (игровые запросы) и `ADMIN` (Spring Security); токен игрока **не должен** открывать `/admin/**`;
- только HTTPS, по возможности ограничение по сети (VPN или внутренняя сеть);
- валидация промпта: лимит длины, обязательные плейсхолдеры (куда подставляются данные запроса), запрет пустого текста;
- допустимые диапазоны настроек (например, таймаут 1–10 с, лимит подсказок 0..N), чтобы опечатка не положила сервис;
- ни ключи, ни персональные данные игроков через админский API не отдаются.

### Ответственность файлов

| Файл | Отвечает за |
|---|---|
| `HintController` | Эндпоинт подсказки: принимает `HintRequest`, валидирует, вызывает `HintService`, возвращает `HintResponse`. Без логики |
| `GlobalExceptionHandler` | 400 при кривом запросе, 429 при исчерпанном лимите, 500 при непредвиденной ошибке. Ошибки нейросети сюда не доходят |
| `dto/*` | Структура JSON-запроса и ответа, преобразование в объекты Java и обратно, валидация аннотациями (`@NotBlank`, `@NotEmpty`, `@Min`). Хранения данных нет |
| `AdminController` | Админский API: версии промптов, настройки, пробный прогон, журнал |
| `domain/*`, `repository/*` | Сущности и доступ к БД только для админской части |
| `HintService` | По порядку: лимит → оценка ходов → промпт → вызов модели → проверка `id` → при сбое запасной вариант. Лимит подсказок хранится здесь же (`ConcurrentHashMap`, не забыть про очистку старых записей) |
| `ActionScorer` | Правила игры: «выгодность» каждого хода по формулам (эффект на показатели, срочность, число оставшихся ходов). Параметры берёт из `SettingsService`. Работает без сети |
| `PromptBuilder` | Берёт активный системный промпт из `PromptService`, подставляет состояние игрока и ходы с оценками в JSON |
| `PromptService` | Версии промптов: создание, активация, откат, запись в журнал |
| `SettingsService` | Настройки с диапазонами значений, хранение в памяти, обновление при записи, запись в журнал |
| `LlmClient` | HTTP-вызов API, структурированный ответ (tool use с `enum` допустимых `id`), таймаут, разбор ответа. Формат конкретного провайдера не выходит за пределы этого пакета |
| `SecurityConfig` | Аутентификация и роли; `/admin/**` только для `ADMIN` |
| `application.yml` | Начальные значения и подключение к БД. Ключ API берётся из переменной окружения `AI_API_KEY` |

## 7. Зависимости

`spring-boot-starter-web`, `spring-boot-starter-validation`, `spring-boot-starter-security`, `spring-boot-starter-data-jpa`, драйвер PostgreSQL (и H2 для локальной разработки), `flyway-core`, `lombok`, `springdoc-openapi` (Swagger для коллеги по Flutter и для админа), `spring-boot-starter-test`.

## 8. Промпт: основа

Промпт хранится в БД и правится админом. Начальная версия (засеять миграцией):

**Системная часть:**
```
Ты помощник в обучающей игре по финансовой грамотности.
Цель игрока: [TODO: формула итогового счёта игры].
Выбирай ход, который лучше всего служит этой цели с учётом числа оставшихся ходов.
Используй переданные оценки ходов как основу, не пересчитывай арифметику сам.
Объясняй просто, в 1-2 предложениях, на «ты», без финансового жаргона.
```

**Пользовательская часть** (собирается кодом): JSON с состоянием игрока, ходами и оценками `ActionScorer`.

Критерий «выгодно» (что считается лучшим ходом) нужно получить от команды: он сильнее всего влияет на качество подсказок.

## 9. Открытые вопросы (к команде)

1. **Список локаций и ходов игры**: `id`, подписи, стоимость во времени, эффект на показатели, условия доступности. **Будет передан позже.** До этого `ActionScorer` и состав `PlayerState` делать расширяемыми, с заглушками и `TODO`.
2. **Как считается победа и «выгодно»**: итоговые очки, баланс показателей, что-то ещё.
3. **Где хранится состояние партии**: на клиенте (приходит в запросе, как в контракте выше) или на сервере (тогда запрос может нести только `gameId`, а сервис читает состояние из общей БД).
4. **Одноуровневая или двухуровневая подсказка**: только ход или локация и действие внутри неё.
5. **Провайдер нейросети и модель**: влияет на формат запроса в `LlmClient`, структура остаётся прежней.
6. **Есть ли общий бэкенд игры на другом языке**: если да, возможно, эндпоинт стоит встроить в него.
7. **Кто будет админом** (разработчики или геймдизайнер): определяет, нужен ли веб-интерфейс поверх админского API. На старте достаточно Swagger или Postman.
8. **Должна ли админка править каталог ходов** (а не только промпт и параметры): заметно увеличивает объём работы.
9. **Есть ли готовая система авторизации** у команды, в которую встроить роль админа.

## 10. Порядок разработки

1. DTO, `HintController`, `GlobalExceptionHandler`, заглушка в `HintService`, возвращающая первый ход. Flutter-коллега может сразу подключаться.
2. `LlmClient` с одним рабочим вызовом API, настройка через `application.yml`.
3. Структурированный ответ (tool use), проверка `id`, запасной вариант по правилам.
4. Подключение БД, Flyway, `PromptService` и `SettingsService`; перенос промпта и параметров из кода в БД.
5. `SecurityConfig` и `AdminController`: версии промптов, настройки, журнал, пробный прогон.
6. `ActionScorer` и `PromptBuilder` под реальные правила игры (после получения списка ходов).
7. Лимит подсказок.
8. Тесты, `Dockerfile`, деплой.

Пункты 4–5 можно сдвинуть после 6, если админка нужна не сразу: до тех пор промпт и параметры лежат в `application.yml`.

## 11. Тесты

- `ActionScorerTest`: эталонные ситуации с заранее известным правильным ходом (например, «через ход аренда, денег впритык, значит не тратить»). Чистая логика, без сети и Spring.
- `HintServiceTest` с заглушкой `LlmClient`: успех, неизвестный `id`, исключение, таймаут, исчерпанный лимит, выключенная нейросеть (должен работать запасной вариант).
- `LlmClientTest` на `MockRestServiceServer` с записанным ответом API.
- Тесты админки: доступ к `/admin/**` без роли `ADMIN` запрещён, валидация промпта и настроек, откат версии, запись в журнал.
- Набор эталонных ситуаций пригодится и для сравнения версий промпта через пробный прогон.

## 12. Требования к надёжности и безопасности (кратко)

- Таймаут вызова нейросети 3–5 секунд, один повтор при временных ошибках (429, 5xx), затем запасной вариант.
- API-ключ только в переменных окружения, не в репозитории и не в БД.
- Аутентификация игровых запросов (токен игрока или сессии), ограничение размера запроса и длины строк.
- В промпт попадают только игровые показатели, без персональных данных игрока.
- Логировать запросы и ответы подсказок (для отладки промпта), без секретов.

## 13. Инструкции агенту

- Не придумывай правила игры. Всё, что зависит от списка ходов и формулы победы, делай расширяемым и помечай `TODO`.
- Не усложняй заранее: не добавляй кэш, Redis, Resilience4j и лишние абстракции, пока нет причины (см. раздел 2 и 7).
- Не выноси в отдельные классы то, что занимает несколько строк (лимит подсказок, проверка `id`).
- Любые изменения промпта и настроек идут только через `PromptService` и `SettingsService` с записью в журнал.
- Проверка `id` ответа модели и запасной вариант обязательны и не отключаются настройками.
- Двигайся по порядку из раздела 10 и после каждого этапа оставляй проект запускаемым.
